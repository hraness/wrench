Design philosophy

Power comes from the boundary.

Wrench is useful because its kernel refuses broad authority. The capability stays small enough to inspect, test, cache, revoke, and reason about when a provider changes.

Intent over mechanism

Operations name the job. Provider requests, browser sessions, cookies, and selectors stay behind the contract.

Evidence before authority

A captured exchange is private evidence. It remains inert until its inputs, outputs, account proof, side effects, and failure behavior are reviewed and tested.

Drift stays visible

When an origin, account, status, field, or response shape changes, the capability stops and returns to capture-required. Wrench never switches to a browser fallback silently.

Unknown stays unknown

Incomplete reads remain incomplete. An ambiguous write stays unsettled until separately obtained evidence can reconcile it.

Local custody

Archives stay inspectable, account-bound reads stay encrypted, and exact cached views can load without a provider roundtrip.

Interchangeable intelligence

Wrench supplies no model, planning loop, approval interface, or application shell. Use the agent system you already prefer.

For technical readers

Small surface. Strong invariants.

Each rule closes a specific failure mode: confused accounts, ambient credentials, provider drift, stale state, duplicated mutations, or trusted code that changed after review.

Strict inputs
Foreign manifests, messages, plans, receipts, responses, and CLI values reject unknown fields and malformed bounds.
Exact identity
Authenticated calls bind one account realm, provider surface, transport, contract version, and implementation identity.
Opaque credentials
Plugins receive declared handles. The caller does not receive cookies, tokens, ambient environment, unrestricted files, a shell, or caller-selected HTTP.
Content-bound trust
Portable-plugin trust applies to one verified bundle. Process separation contains ordinary failures and is not described as a hostile-code sandbox.
Last-good reads
Exact snapshots preserve provider paging and completeness. A failed refresh or drifted projection does not erase the last verified state.
At-most-once evidence
Consequential changes require a short-lived exact preview and confirmation. An indeterminate dispatch is reconciled from separate evidence and never blindly retried.

The important limits

Questions Wrench should answer plainly.

Is Wrench an AI agent?

No. Wrench provides @hraness/wrench, a CLI, and an SDK. Your agent owns the model, planning loop, approvals, and interface.

Does it work with every service?

No. Public capture and authenticated provider operations have different boundaries. wrench capabilities is the source of truth for operations installed and observed on the current machine.

Does it bypass login, paywalls, access controls, or DRM?

No. Media acquisition is limited to one authorized, accessible, finite, non-DRM item. Wrench does not bypass payment, authentication, access controls, or DRM.

What happens when a provider changes?

The affected operation fails closed and returns to capture-required until a new contract is captured, reviewed, and tested. Wrench does not switch to a browser fallback silently.

Why does Wrench refuse to retry some writes?

If a request left the machine and its response was lost, the effect may already exist. Wrench retains that uncertainty and reconciles it from separately obtained evidence.
